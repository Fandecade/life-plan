# Life Planner 改进计划（2026-11-24）

> 来源：项目外的第三方梳理与建议文档《梳理项目并提建议》，结合现有代码与 105 项测试评估后整理。
> 原则：不堆功能，先补齐「能力成长可验证」这条主线；所有改动必须可编译、可测试、可回滚。

---

## 一、总体判断

原文对项目的定位是准确的：

> 一个以长期能力成长为核心的个人自我管理与发展系统：帮助人建立方向、形成能力、持续行动、创造成果，并通过反馈不断调整路径。

项目**不缺功能与理论**，真正欠缺的是三件事：

1. **理论之间的关系**：目标设定 / 自我决定 / 控制论 / 实施意图 / 福格 / 刻意练习 / 检索练习 / 元认知 需要各自绑定到明确机制，而不是并列陈列。
2. **成长效果的衡量方式**：目前能回答「做了什么、花了多少时间、是否坚持、是否学完」，但还不能回答「这些投入让人获得了什么新能力」。
3. **系统对行为的干预方式**：从「记录 + 统计」升级为「识别偏差 → 判断原因 → 选择调整 → 验证效果」的闭环。

### 必须保留的三个设计
- 目标—能力—任务三级结构（后续扩展为 目标—能力—阶段成果—任务）
- 输出式学习：以独立输出而非输入量作为掌握判据
- 复盘能直接改写其他模块（排期、复习、配方、归档）

### 两条贯穿全产品的原则
- **系统负责提供反馈，不负责给人打分**（延续福格模块的温和原则）
- **自主性 + 可持续性**优先于「完成更多」

## 二、理论底座与产品机制映射

| 理论 | 绑定模块 | 产品机制（本仓库对应实现） |
|---|---|---|
| Goal-Setting Theory | 人生规划 | 愿景 / 能力 / 阶段成果 / 任务；阶段成果作为能力验收标准 |
| Self-Determination Theory | 全产品 | 可自由调整/放弃目标；展示真实进步；不做考勤式评判（「节奏偏缓」） |
| Control Theory（自我调节） | 及时复盘 | 目标 vs 实际 → 偏差 → 调整 → 下期验证 |
| Implementation Intentions | 时间盒 / 任务 / 复盘 | If–Then 预案（任务字段 + 复盘 If–Then） |
| Fogg Behavior Model | 福格习惯 | 锚点 / 微行为 / 庆祝 / 5 维阻力 / 行动线推演 |
| COM-B | 福格习惯诊断 | 能力 / 机会 / 动机三层诊断，与 5 维阻力并存 |
| Deliberate Practice | 能力建设 | 阶段成果 + 成果证据，避免「完成任务 = 掌握能力」 |
| Retrieval & Spacing | 输出式学习 | 主动回忆、动态间隔、连续顺畅提前通关 |
| Metacognition & SRL | 学习 + 复盘 | 卡点速记、策略回看、调整效果验证 |

**边界声明**：行动线公式 `required(ability) = threshold + (10 - threshold) × (1 - ability/10) ^ curvature` 是产品启发式模型，不是福格理论原式，也不是个体行为预测器。

## 三、改进项清单

状态说明：`✅ 本轮完成` / `🕓 后续批次（已在本文档给出设计）`

### I1. 能力阶段成果 Milestone（P0）✅
- **问题**：能力只有任务堆叠，缺少「达到什么水平」的验收标准。
- **方案**：`Capability` 新增 `milestonesJson`，每项包含 `id / title / evidence / achieved / achievedAt`。
- **交互**：能力节点菜单「阶段成果」→ 弹窗添加、标记达成、删除、填证据链接；能力卡片显示 `阶段成果 x/y`。
- **验收**：可增删改并持久化；图谱与重启后一致；阶段成果不计入任务数。

### I2. 成果证据 Artifact（P0）✅
- **问题**：学习成果散落在外部链接与文本中，无法回答「某项能力有哪些证据」。
- **已实现**：新增 `Artifact` 实体（`artifacts` box）：`capabilityId / actionItemId / sessionId / type（概念解释/推导/习题/代码/项目/表达）/ title / url / note`。
- **入口**：输出成果库 → 查看成果 →「记为能力成果」→ 选择类型/关联能力/链接 → 保存。
- **展示**：能力「阶段成果」弹窗列出「能力证据 · N」；Milestone 仍保留 evidence 链接字段。
- **后续**：年复盘成果精选优先从 Artifact 取数；Project 与 Artifact 的多对多关系。

### I3. 任务多时间块（P0）✅
- **问题**：现有 `ActionItem → TimeBlock` 以单块为主，难以表达「同一任务多次推进」。
- **已实现**：`TimeBlockRepository.blocksForActionItem` 返回全部块；`scheduleAction(append: true)` 追加而不覆盖；`forActionItem` 兼容返回「当前块」；任务详情新增「再排一次」并显示共 N 次排期。
- **验收**：同一任务可同时存在多块；默认排期仍只更新一块（旧行为不变）；复盘/月视图按块遍历天然兼容。

### I4. 复盘调整效果验证（P0）✅
- **问题**：复盘只能写「下次注意」，无法验证调整是否有效。
- **方案**：`ReviewLog` 新增 `adjustmentPlan / expectedOutcome / actualOutcome`。
- **交互**：
  - 周/月复盘问答新增「本期调整方案」「预期效果（可验证）」。
  - 下一周期打开时显示「上期调整回看」卡片，可补填「实际效果」并写回上一期记录。
- **验收**：跨周期能读回上期方案与预期；实际效果保存到上期 log。

### I5. If–Then 行动预案（P1）✅
- **方案**：`ActionItem.ifThenText`；任务详情抽屉可编辑。
- **验收**：任务详情中可写入并持久化，时间盒/复盘读取同一字段。

### I6. 认知负荷（P1）✅
- **方案**：`ActionItem.cognitiveLoad`（低/中/高，默认中）；任务详情三选一。
- **后续**：周复盘按负荷统计投入结构，高负荷连续排期提醒。
- **验收**：字段可保存；复盘快照统计高/中/低负荷分钟数。

### I7. COM-B 诊断（P1）✅
- **方案**：行动线诊断面板增加一行 COM-B 分类提示：
  - 能力：体力/脑力阻力
  - 机会：时间/日程/金钱阻力
  - 动机：动机缺口/庆祝与锚点不足
- **验收**：提示随阻力与落点变化；不替代 5 维阻力清单。

### I8. 数据备份与恢复（P0）✅
- **方案**：`LocalDatabase.exportJson()` / `importJson()`（13 个业务 box，不含设置）；设置页提供「导出到剪贴板」「从剪贴板恢复」（二次确认）。
- **限制**：导入后当前进程内页面不自动刷新，提示用户重启；附件一致性留待 Artifact 落地后统一处理。
- **验收**：导出→清空→导入可完整还原实体数据。

### I9. 能力 / 项目实体分离（P0）🕓
- **设计**：`Vision → Capability → Milestone → Project / ActionItem`；Project 拥有阶段、产物、关联能力与验收标准，不塞进 3 级任务树。
- **后续**：新增 Project 模块页与 `projects` box；ActionItem 增加可选 `projectId`。

### I10. 指标体系分层（P1）✅
- **已实现**：周/月/年复盘新增「指标分层」卡，五类指标分列呈现，不合成总分：
  - 执行：计划 vs 实际时长
  - 学习：独立输出、按时回忆率
  - 能力：阶段成果达成数 + 成果证据数
  - 习惯：节律稳定度
  - 对齐：前两项能力的时间占比
- **后续**：同一套口径复用到图谱与时间盒页面，并加入跨周期趋势。

### I11. 时间盒负荷与缓冲（P1）✅
- **已实现**：复盘快照按任务认知负荷统计高/中/低分钟数；周/月/年复盘新增「认知负荷结构」卡片（三条细进度条 + 时长）；高负荷占比 > 60% 时提示「保留 10–15% 缓冲与恢复时间」。
- **后续**：在日视图提供可配置的「计划缓冲比例」，并在连续高负荷日自动建议插入恢复块。

### I12. 根因判断（P0）✅
- **已实现**：每类待校准事项的「⋯」新增「判断原因并调整…」，先选原因再执行对应动作：
  - 目标过大 → 去图谱拆解 / 重新安排
  - 能力不足 → 生成补盲任务 / 拆解
  - 时间不足 → 重新安排时间
  - 行为阻力 → 调习惯配方
  - 目标不再重要 → 归档 / 取消
  - 估时不准 → 重新安排并调整时长
- **后续**：把根因作为字段持久化，并支持连续追问（5 Whys）与原因分布统计。

### I13. 学习策略有效性（P2）✅
- **已实现**：按「知识类型 + 输出档位」汇总复习顺畅率（样本 ≥ 2），周/月/年复盘新增「学习策略有效性」卡，展示前三项有效策略。
- **后续**：跨更长周期与更多卡点维度细分，给出个性化方法建议。

### I14. 多端同步与冲突处理（P2）🕓
- 现有 `syncStatus` 仅预留；接入服务端时需补冲突策略与幂等。
